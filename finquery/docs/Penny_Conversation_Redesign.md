# Penny — Conversational Intelligence Redesign (Architecture Review + Design)

> Deliverable for the "redesign the conversation pipeline" mandate. Produced from an
> 8-agent architecture audit of `scripts/test_server.py` (3,707 lines), `txn_store.py`,
> and `ml_insights.py`. **91 context-loss points** were catalogued (12 critical, 36 high,
> 36 medium, 7 low) plus a 17-family re-inference call-site inventory. The deterministic
> SQL engine (`txn_store`) is Penny's crown jewel and is **frozen** — the redesign changes
> only how the conversation/routing layer *feeds* it.

## 1. Executive summary — the one root cause

Every context-loss symptom the client reported (Bupa answered "in July" because a prior turn
said July; "insights in this category" drifting to Shopping; "how much did I spend?" leaking a
merchant; filters that don't compose) traces to a **single structural flaw**:

> `_resolve_conversation` computes a fully-structured scope (merchant, category, period,
> filters, metric), **persists it to `ctx`, then throws it away** and hands downstream engines
> only a *rewritten English string* `rq`. Every engine — `analytics_answer`, `concept_answer`,
> `_resolve_factual`, `grounded_advice`, `intelligence_answer`, `ml_answer`, the LLM router —
> then **re-infers period / merchant / category / amount from that text**, each with its own,
> subtly-different parser.

Consequences, all confirmed in the audit:
- **`_extract_slots` runs 2× per turn** (once on `q`, once on `rq`); the LLM router re-parses a
  3rd time; `_apply_guards` a 4th. Period is re-inferred at **6+ entry points**; merchant
  matching exists in **≥5 different matchers** with different fuzz rules.
- The **period-carry ladder is copy-pasted** between `_resolve_conversation` and
  `_resolve_factual` (the code comment literally says "mirror _resolve_factual") and the two
  copies **diverge** on the same input.
- `ConversationState.filters` is **declared but dead** — weekend/exclusion filters are parsed
  only as a routing gate, never carried or applied. Grouping is conflated into `metric`
  ("breakdown" hardwired to by-month). There is **no** active-transaction handle, no structured
  last-result, no `previous_sql`, no confidence.
- **ML and every intelligence engine ignore period and entity entirely** — they always query
  `ts.*(USER)` with `period=None`. `dispatch_intent` is always called `doc_name=None`, dropping
  account scope on the whole factual path.
- The **follow-up path is the one place a number can be hallucinated** — `followup_response`
  answers from a 200-char prose snippet with no SQL verification.

## 2. Target architecture — one canonical query, consumed everywhere

```
User Question
  ↓ Normalize            (currency/word-number/whitespace; anchor dates resolved once)
  ↓ DialogueState        (typed, full dialogue memory — loaded from thread ctx)
  ↓ Reference resolution (this/that category|merchant → carried name)
  ↓ Pronoun resolution   (it/that/them/one → carried entity OR active_transaction)
  ↓ Ellipsis resolution  (bare "average" / "only June" / "per month" → canonical metric+scope)
  ↓ Entity resolution    (merchant · category · concept — ONE matcher, ambiguity→clarify)
  ↓ Intent resolution    (intent_family + metric from verbs; operation, not context)
  ↓ Time resolution      (ONE time engine: explicit · relative · quarter · half · window)
  ↓ Filter resolution    (composable: txn_type · amount±N · weekend · exclude · group_by)
  ↓ Comparison resolution(entity-pair or period-pair, persisted)
  ↓ Context-priority merge  explicit(this turn) > DialogueState > last-result-meta > history
  ↓ ── CanonicalQuery ──  (the single typed object; NO engine re-parses after this)
  ↓ Routing decision     (intent_family → engine; keyed off CanonicalQuery fields)
  ↓ SQL / Analytics / ML / Advice / Concept   (each READS cq.*, never re-infers)
  ↓ Response formatter   (structured conversational answer; every figure from SQL)
  ↓ DialogueState update (deterministic per-field rules; writes active_transaction + last_result)
```

**`CanonicalQuery`** (single typed object, superset of today's `intent` dict):
`raw · intent_family · intent/metric · merchant · category · concept · period{start,end,grain,
year_source} · period_list · aggregation · group_by · txn_type · count_kind · filters{weekend,
exclude[]} · amount_op · amount · comparison[] · n · sort · doc_name · date_dir · special
payloads · options/phrase (clarify) · signals · confidence`.
`cq.to_intent()` emits **exactly** today's `dispatch_intent` dict, so the factual path is
behaviourally identical (guarded by a differential over 1,000 questions).

**`DialogueState`** (upgraded `ConversationState`) adds the fields the audit found missing:
`active_transaction{id,date,merchant,category,amount,direction}` · `last_result{value(s),unit,
rows[],ordering,rowcount,entity_list,intent,period,route}` · `previous_sql/prev_spec` ·
`group_by` · composable `filters` · `amount_threshold+direction` · `exclude[]` · `comparison` ·
`presentation(table|line|bar|pie)` · `confidence`. Each field has **one** explicit update rule.

**Context priority (never overwrite explicit user input):**
`explicit this-turn slot` **>** `DialogueState carried` **>** `last-result metadata` **>** `history`.

## 3. Determinism invariants (must not break)

1. Every number comes from `txn_store` SQL — never the LLM. The follow-up path (today
   unverified) MUST answer from structured `last_result` or pass the `_advice_grounded` number
   check. This closes the one hallucination hole.
2. `txn_store.dispatch_intent` + the `(user_id, doc_name, period)` + `_scope` contract is
   frozen; `CanonicalQuery` maps ONTO these signatures (period forms: `None | 'YYYY[-MM[-DD]]'
   prefix | (start,end) | 'MD-MM-DD'`).
3. Fresh thread (empty ctx) = passthrough — single-turn suites (golden, 1000-factual) unaffected.
4. The **R13 rule** (a syntactically complete question does NOT inherit the prior merchant) is
   preserved *and extended to period* (CLP-04) and to entity-change (CLP-05).
5. Zero-result / unknown entity → honest "no transactions found", never carried as scope, on
   ALL paths (today only the two SQL paths).
6. Concept answers compute only from matched real merchants or say "couldn't find any".
7. Ambiguous merchant → clarify ("ask, don't guess"), extended to every merchant mention.

## 8. What the LLM does (and never does)

The LLM is demoted to two jobs: (1) a thin **fallback** intent classifier when the deterministic
resolver is uncertain, and (2) **language generation** for advisory prose. It never sees the
transaction table, never chooses the topic (the resolver pins it), and never emits a number that
isn't validated against the SQL fact sheet. Every financial figure remains SQL-sourced.
